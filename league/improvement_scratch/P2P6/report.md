## Part 1 — P2: design-seal tooling + contamination scanner

### The design rule (going forward)

EDA and reliability artefacts may only be computed on **dev-era
seasons**. Sealed-season aggregates are generated by the coordinator
after the design document freezes, and are never shown to builders.
This is the fix for AUDIT.md §4(b): the completed program was
fit-sealed but **not design-sealed** — EDA workbooks inspected
aggregates across all seasons, so sealed-season levels were printed
in design documents (the AE-ProLeague F1 table literally contains a
row labelled "2025/2026 (virgin)").

### Deliverable A — shared dev-era filter (`league/design_seal/`)

How EDA artefacts were generated in the completed program: each
league has its own generator under `league/<L>/analysis/`
(`eda_compute.py` / `eda.py` / `run_eda.py`, plus `make_charts.py`)
writing `eda_numbers.json` / `eda_summary.json` and the `EDA.md` /
`FEATURES.md` / `MODEL_DESIGN.md` documents. There was no shared
filter — the AE generator, for example, loops `SEASONS` = all six
seasons for its level table, uses `SEASONS[:5]` (including the
virgin) for split-half reliability, and a splits-era window that
includes the virgin season for halves shares.

The shared utility now lives in `league/design_seal/`:

- `seal.py` — `load_seal(league_dir)` builds the dev/sealed partition
  from the league's own `config.yaml` (dev = `dev_seed` +
  `dev_period`; sealed = `virgin_primary` + `virgin_confirmatory` /
  any `virgin*` season key; the parser is dependency-free — the
  project venv has no PyYAML — and handles the config variants found
  in the tree: flow lists, nested virgin keys, `virgin:` blocks,
  explicit `null`/`none`, and rejects non-season values riding on
  virgin metadata keys). `filter_rows(rows, seal)` drops sealed (and
  unlabelled / non-dev) rows; `assert_dev_only(obj, seal)` raises
  `SealViolation` if a JSON-like artefact contains a sealed-season
  key or value; `find_sealed_references()` / `text_mentions_sealed()`
  support the scanner.
- `eda_filter.py` — the CLI wrapper an EDA generator uses
  (`filter-csv` → dev-only CSV; `check-json` → exit 1 if an artefact
  is contaminated), plus the in-code pattern in the README.
- `README.md` — the design rule, usage, Gate Zero framing, and the
  scanner's stated limits.

## Part 2 — P6: worst-fold dev reporting tool

### Tool (`league/worst_fold/`)

`worst_fold.py` reads a league's persisted dev artefact
(`engine/<market>/results_dev.json`) and emits the verdict-format
block: pooled legs beside the worst dev season's legs, per arm and
per baseline. The fold is defined by the reference arm (Gate Zero)
at the primary metric (LL at the primary line; 1X2 LL for goals);
pooled values are taken from the artefact when persisted, otherwise
computed as the n-weighted mean of per-season LLs and labelled as
computed. `--json` writes the full per-season extraction.

The completed program persisted `results_dev.json` in many shapes;
the extractor normalises the common ones (arm/baseline
`pooled`+`seasons` blocks, nested series-per-season blocks, row
lists, `metrics` blocks, `logloss`-by-line cells, `primary_ll`
rows). Sweep over all 428 persisted dev artefacts in the tree:
**373 (87%) are extractable today**; the rest are one-off layouts.
For new builds, the arm/baseline `pooled`+`seasons` shape is the
recommended artefact layout (see `league/worst_fold/README.md`).

**P6 has no statistical Gate Zero** (it changes no gate and no
verdict — information only, adoptable independently per AUDIT.md
§6). **The tool is ready for the coordinator to mandate in this
program's verdict format**: append the emitted block to every
verdict, next to the pooled legs.
